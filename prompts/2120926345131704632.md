## Prompt (English)

```text
Build two dev-only "lookbook" pages for this app, made from its real code, that show its whole visual language:

1. /lookbook/parts: every shared UI part, in every variant and state, on every surface it can sit on.
2. /lookbook/art: every visual asset (icons, illustrations, logos, images, patterns), with each theme's version side by side.

First scan the repo and list what you find: the stack and routing, how styling works (CSS, Tailwind, tokens, CSS-in-JS), any themes (light/dark, brands) and how they switch, the shared components, and where assets live (icon packages and inline SVGs too). Then build. Only ask if you can't tell how pages are routed or themed.

Parts
- Render the real components or classes, inside the app's own layout, with stand-in data. Recreate and restyle nothing.
- Cover surfaces (page, cards, panels, dark insets), headings and text, buttons (every variant, size and state), links, form fields (with help text, with an error, disabled), checkboxes and radios, alerts, badges, cards, menus, tabs, pagination, tables, empty states, avatars, code, rendered markdown, loaders, and anything else shared.
- Show the states markup can express (disabled, invalid, selected, open, loading); leave hover and focus live. Render overlays (modals, toasts, tooltips) open, in the page's flow.
- Label each section with the component's name and file.
- Stand-in data stays in the page: nothing saved, no requests, forms don't submit.
- Follow the current theme, with the app's theme switch on the page if it has one.

Art
- One row per asset: its name, then each theme's version on a checkerboard so edges show, with file sizes.
- Flag versions missing from a theme and files nothing uses. Assemble multi-piece assets as the app shows them; let animated ones animate.

Rules
- Register both routes for local development only, the framework's usual way, so they never ship. Don't link them from the app.
- Put new files in one place. Touch existing files only to add the routes, and delete nothing. Show what exists rather than designing new parts; anything that can't be shown as it is goes in the report.

Check: run the app, open both pages in every theme at phone and desktop widths, and fix console errors, missing assets, sideways scrolling and unstyled parts. If the repo has tests, add one that the pages render in development and 404 in production.

Finish with a short report: the URLs, counts per group, and what you noticed: near-duplicate components, one-off colours or sizes that skip the tokens, text below WCAG AA contrast, assets missing from a theme, unused files, and parts with no error or disabled state.
```
